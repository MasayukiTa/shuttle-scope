# 映像経路の設計 (MEDIA_PATH v1)

状態: **草案 / 意思決定中**
最終更新: 2026-08-15
関連: `backend/ws/camera.py`, `src/components/session/DeviceManagerPanel.tsx`,
`src/pages/CameraSenderPage.tsx`, `src/pages/ViewerPage.tsx`

この文書は「複数カメラの映像が誰を経由して視聴者に届くか」を決めるためのもの。
実装が分岐を抱えており、分岐の理由が暗黙知になっていたので明文化する。

---

## 1. 経緯 — なぜ分岐が生まれたか

当初の想定は **各会場に解析用 PC を置く** ことだった。カメラ (iOS) と PC が
同じ LAN に居るので、WebRTC は LAN 内 P2P で完結し、上り帯域も遅延も問題に
ならない。現行実装はこの前提でできている。

その後、運用の想定が変わった。

- 解析者が現地に居ない場合がある
- 視聴者は遠隔から入る
- 会場に PC を置ける場合と置けない場合の両方がある

この結果、「映像をサーバへ送って再配布する」経路が必要になった。しかし実装は
当初の前提のままなので、**現行コードには経路の概念そのものが無い**。
operator PC が中継役であることがハードコードされている。

分岐が難しく感じられるのはこのためで、分岐の置き場所が決まっていないから。

---

## 2. 現状の実装資産 (2026-08-15 時点の実測)

| 経路 | 実在 | 実体 |
|---|---|---|
| カメラ → operator PC | あり | WebRTC。`camera.py` が SDP/ICE を中継 |
| operator PC → viewer | あり | operator が viewer ごとに PeerConnection を張り直す |
| カメラ → サーバ (録画) | あり | `useServerSideRecording`。MediaRecorder を 10 秒刻みで chunked HTTP upload。**リアルタイムではない** |
| operator PC → サーバ (CV) | あり | `useRealtimeYolo`。640×360 / JPEG q0.55 / 10fps を WS 送信 |
| カメラ → サーバ (リアルタイム映像) | **なし** | — |

重要な帰結:

- **サーバは WebRTC の映像を一度も受け取っていない。** 映像に関する
  サーバの入力は「端末からの録画チャンク」と「operator ブラウザからの JPEG」だけ。
- したがって **CV の画質は operator のブラウザが決めている**。
  640×360 の JPEG q0.55 が解析の入力になっている。
- SFU 系の依存 (aiortc / mediasoup / LiveKit) は未導入。
- TURN は DB Settings の任意項目。既定は STUN のみ。

補足: Cloudflare tunnel は HTTP/WS しか通さない。**WebRTC の映像は
tunnel を通らない**。「Cloudflare を介す/介さない」という論点が当てはまるのは
録画アップロードと signalling であって、WebRTC 本体ではない。
WebRTC が NAT を越えられないときに経由するのは TURN であり、TURN を
自宅に置けば自宅の回線を通る。

## 3. 経路の選択肢

用語: **メディアハブ** = カメラの映像を受け取り、視聴者へ配る主体。

### A. ローカル PC ハブ (現行の前提)

会場に operator PC があり、カメラと同一 LAN。

- 映像は会場 LAN 内で完結。上り帯域の消費なし、遅延最小
- 遠隔視聴者が居る場合のみ、会場の上りに `視聴者数 × カメラ数` が乗る
- operator のブラウザが視聴者ごとに再エンコードする (CPU 律速)
- PC が会場に無い運用では成立しない

### B. リモート PC ハブ (現行コードを遠隔運用に流用した状態)

会場のカメラ → インターネット → 解析者宅の PC → インターネット → 視聴者。

- **現行コードで遠隔運用すると自動的にこうなる。意図した設計ではない**
- 会場の上りに N 本、解析者側の上りに N×V 本
- operator のブラウザが N 本の受信 + N×V 本の送信を担う。最も CPU が苦しい
- ブラウザのタブが閉じた瞬間に全視聴者が切れる

### C. サーバハブ (SFU)

会場のカメラ → サーバ → 視聴者 / operator。

- 帯域は B と同オーダー (サーバが自宅にあるため、自宅回線に N 下り + N×V 上り)。
  **帯域は B の解決策にならない。** ここを取り違えないこと
- 利点は帯域ではなく次の三つ:
  1. **CPU**: SFU は再エンコードせず RTP を転送するだけ。ブラウザの N×V
     エンコードが消える
  2. **可用性**: サーバは常時稼働。operator のブラウザに依存しない。
     解析者が接続していなくても録画と配信が続く
  3. **映像の正本がサーバに来る**。CV が operator ブラウザの
     640×360 JPEG に依存しなくなり、録画も WebRTC 経路と一本化できる
- 代償: SFU の導入 (未依存)。API プロセスとは別プロセスが必要

### D. カメラ → 視聴者 直 P2P

カメラ 1 台・視聴者 1 人でしか成立せず、カメラ側 (iOS) の上りと電池を
視聴者数ぶん消費する。**採らない。**

## 4. 分岐をどこに置くか — 設計の核

分岐が難しいのは、分岐をカメラ側と視聴者側に持たせようとするから。

**カメラと視聴者にはハブの正体を知らせない。** これが本設計の要点。

- カメラは常に「ハブ」へ offer を出す
- 視聴者は常に「ハブ」から購読する
- どちらも宛先を指定しない。**signalling サーバだけがハブの正体を知る**

`camera.py` は現在 `webrtc_offer` を無条件に operator ソケットへ中継している。
ここを「セッションの `media_hub` 設定を見て、operator ソケットへ流すか、
内部 SFU へ渡すか」に変えるだけで分岐が閉じる。プロトコルは一つのまま。

```
device ──webrtc_offer──> signalling ──┬─> operator socket   (media_hub=local_pc)
                                      └─> 内部 SFU          (media_hub=server)
```

この形なら:

- iOS 側のコードは経路を意識しない (現地/遠隔で同じアプリ)
- 視聴者側も同じ
- 経路の変更がサーバ設定の変更だけで済む
- 将来 SFU を差し替えても端末に影響しない

### 経路の決め方

自動判定 (operator とカメラが同一 LAN か) は誘惑的だが脆い。NAT 構成や
ゲスト SSID 分離で簡単に誤判定する。**セッション単位の明示設定を正とする。**

- セッション作成時に `media_hub` を選ぶ (既定は `server`)
- UI に現在の経路を常時表示する。どちらで動いているか分からない状態を作らない
- `local_pc` を選んだセッションで一定時間内に P2P が確立しなければ
  `server` へフォールバックし、フォールバックしたことを UI に出す

**「勝手に切り替わったが誰も気づかない」を作らないこと。**
過去に、決定論的に判定できるものをヒューリスティックで代替して
実害を出している (メニュー識別・画面生存性の件)。同じ轍を踏まない。

## 5. 推奨

**サーバハブ (C) を既定とし、ローカル PC ハブ (A) を最適化として残す。**

理由:

- 運用の想定が「解析者は現地に居ないかもしれない」に変わった以上、
  operator PC をハブにする設計は前提を失っている
- サーバは録画と CV のために**どのみち映像を必要としている**。
  いま operator ブラウザが JPEG に落として渡しているのは、
  ハブが operator だったことの副産物にすぎない
- 会場に PC がある場合の A は帯域と遅延で明確に優れるので、捨てずに残す

B (リモート PC ハブ) は**意図的に選ぶ対象ではない**。現行コードを遠隔で
使うと自動的に B になる、という事実を認識しておく必要がある。

### 段階

1. **プロトコルをハブ非依存にする** (挙動不変)
   `stream_id` 導入、カメラ/視聴者から宛先指定を除去、
   `media_hub` をセッション属性として持つ (値は `local_pc` のみ)
2. **operator を複数カメラ対応にする** (`Map<streamId, PeerConnection>`)
   — ハブが operator のままでも多カメラは成立させる必要がある
3. **サーバハブを追加** (aiortc + MediaRelay を別プロセスで)
   `media_hub=server` を選べるようにする。CV の入力をここへ移す
4. **フォールバックと表示**
5. 録画を WebRTC 経路へ一本化 (現在の chunked upload は経路が二重)

段階 1 と 2 はハブの選択に関係なく必要で、いま着手できる。
段階 3 が最大の投資判断。

## 6. 未決事項

- SFU の実体: aiortc (Python・既存スタックに載る・CPU が読めない) か、
  LiveKit 等の別サービス (堅いが運用対象が増える) か
- 同時カメラ本数と視聴者数の上限。実測が要る。
  現行の `MAX_VIEWERS_PER_SESSION = 30` は**根拠がなく、撤回すべき**
- TURN をどこに置くか。自宅に置けば自宅回線を通る。
  置かない場合、会場のゲスト Wi-Fi (UDP 遮断 / client isolation) で
  P2P が張れず、映像が出ないという故障が起きる
- 録画の正本をどちらにするか (端末アップロード / サーバ受信)
- 会場に PC がある構成で、その PC は operator なのか単なるハブなのか
