# 映像経路の設計 (MEDIA_PATH v1)

状態: **草案 / 意思決定中**
最終更新: 2026-08-15
関連: `backend/ws/camera.py`, `src/components/session/DeviceManagerPanel.tsx`,
`src/pages/CameraSenderPage.tsx`, `src/pages/ViewerPage.tsx`

この文書は「複数カメラの映像が誰を経由して視聴者に届くか」を決めるためのもの。
実装が分岐を抱えており、分岐の理由が暗黙知になっていたので明文化する。

---

## 1. 経緯 — なぜ分岐が生まれたか

当初の想定は **各会場に解析用 PC を置く** ことだった。カメラ (iOS) と PC が
同じ LAN に居るので、WebRTC は LAN 内 P2P で完結し、上り帯域も遅延も問題に
ならない。現行実装はこの前提でできている。

その後、運用の想定が変わった。

- 解析者が現地に居ない場合がある
- 視聴者は遠隔から入る
- 会場に PC を置ける場合と置けない場合の両方がある

この結果、「映像をサーバへ送って再配布する」経路が必要になった。しかし実装は
当初の前提のままなので、**現行コードには経路の概念そのものが無い**。
operator PC が中継役であることがハードコードされている。

分岐が難しく感じられるのはこのためで、分岐の置き場所が決まっていないから。

---

## 2. 現状の実装資産 (2026-08-15 時点の実測)

| 経路 | 実在 | 実体 |
|---|---|---|
| カメラ → operator PC | あり | WebRTC。`camera.py` が SDP/ICE を中継 |
| operator PC → viewer | あり | operator が viewer ごとに PeerConnection を張り直す |
| カメラ → サーバ (録画) | あり | `useServerSideRecording`。MediaRecorder を 10 秒刻みで chunked HTTP upload。**リアルタイムではない** |
| operator PC → サーバ (CV) | あり | `useRealtimeYolo`。640×360 / JPEG q0.55 / 10fps を WS 送信 |
| カメラ → サーバ (リアルタイム映像) | **なし** | — |

重要な帰結:

- **サーバは WebRTC の映像を一度も受け取っていない。** 映像に関する
  サーバの入力は「端末からの録画チャンク」と「operator ブラウザからの JPEG」だけ。
- したがって **CV の画質は operator のブラウザが決めている**。
  640×360 の JPEG q0.55 が解析の入力になっている。
- SFU 系の依存 (aiortc / mediasoup / LiveKit) は未導入。
- TURN は DB Settings の任意項目。既定は STUN のみ。

補足: Cloudflare tunnel は HTTP/WS しか通さない。**WebRTC の映像は
tunnel を通らない**。「Cloudflare を介す/介さない」という論点が当てはまるのは
録画アップロードと signalling であって、WebRTC 本体ではない。
WebRTC が NAT を越えられないときに経由するのは TURN であり、TURN を
自宅に置けば自宅の回線を通る。

## 3. 経路の選択肢

用語: **メディアハブ** = カメラの映像を受け取り、視聴者へ配る主体。

### A. ローカル PC ハブ (現行の前提)

会場に operator PC があり、カメラと同一 LAN。

- 映像は会場 LAN 内で完結。上り帯域の消費なし、遅延最小
- 遠隔視聴者が居る場合のみ、会場の上りに `視聴者数 × カメラ数` が乗る
- operator のブラウザが視聴者ごとに再エンコードする (CPU 律速)
- PC が会場に無い運用では成立しない

### B. リモート PC ハブ (現行コードを遠隔運用に流用した状態)

会場のカメラ → インターネット → 解析者宅の PC → インターネット → 視聴者。

- **現行コードで遠隔運用すると自動的にこうなる。意図した設計ではない**
- 会場の上りに N 本、解析者側の上りに N×V 本
- operator のブラウザが N 本の受信 + N×V 本の送信を担う。最も CPU が苦しい
- ブラウザのタブが閉じた瞬間に全視聴者が切れる

### C. サーバハブ (SFU)

会場のカメラ → サーバ → 視聴者 / operator。

- 帯域は B と同オーダー (サーバが自宅にあるため、自宅回線に N 下り + N×V 上り)。
  **帯域は B の解決策にならない。** ここを取り違えないこと
- 利点は帯域ではなく次の三つ:
  1. **CPU**: SFU は再エンコードせず RTP を転送するだけ。ブラウザの N×V
     エンコードが消える
  2. **可用性**: サーバは常時稼働。operator のブラウザに依存しない。
     解析者が接続していなくても録画と配信が続く
  3. **映像の正本がサーバに来る**。CV が operator ブラウザの
     640×360 JPEG に依存しなくなり、録画も WebRTC 経路と一本化できる
- 代償: SFU の導入 (未依存)。API プロセスとは別プロセスが必要

### D. カメラ → 視聴者 直 P2P

カメラ 1 台・視聴者 1 人でしか成立せず、カメラ側 (iOS) の上りと電池を
視聴者数ぶん消費する。**採らない。**

## 4. 分岐をどこに置くか — 設計の核

分岐が難しいのは、分岐をカメラ側と視聴者側に持たせようとするから。

**カメラと視聴者にはハブの正体を知らせない。** これが本設計の要点。

- カメラは常に「ハブ」へ offer を出す
- 視聴者は常に「ハブ」から購読する
- どちらも宛先を指定しない。**signalling サーバだけがハブの正体を知る**

`camera.py` は現在 `webrtc_offer` を無条件に operator ソケットへ中継している。
ここを「セッションの `media_hub` 設定を見て、operator ソケットへ流すか、
内部 SFU へ渡すか」に変えるだけで分岐が閉じる。プロトコルは一つのまま。

```
device ──webrtc_offer──> signalling ──┬─> operator socket   (media_hub=local_pc)
                                      └─> 内部 SFU          (media_hub=server)
```

この形なら:

- iOS 側のコードは経路を意識しない (現地/遠隔で同じアプリ)
- 視聴者側も同じ
- 経路の変更がサーバ設定の変更だけで済む
- 将来 SFU を差し替えても端末に影響しない

### 経路の決め方

自動判定 (operator とカメラが同一 LAN か) は誘惑的だが脆い。NAT 構成や
ゲスト SSID 分離で簡単に誤判定する。**セッション単位の明示設定を正とする。**

- セッション作成時に `media_hub` を選ぶ (既定は `server`)
- UI に現在の経路を常時表示する。どちらで動いているか分からない状態を作らない
- `local_pc` を選んだセッションで一定時間内に P2P が確立しなければ
  `server` へフォールバックし、フォールバックしたことを UI に出す

**「勝手に切り替わったが誰も気づかない」を作らないこと。**
過去に、決定論的に判定できるものをヒューリスティックで代替して
実害を出している (メニュー識別・画面生存性の件)。同じ轍を踏まない。

## 5. 推奨

**自宅内の隔離したノードをハブ (SFU + TURN) とし、
ローカル PC ハブ (A) を最適化として残す。** 具体構成は 5.7 節。

外部の事業者とは契約しない (VPS / Cloudflare Realtime は選択肢外)。
5.5〜5.6 の検証で分かったのは「自宅に置くな」ではなく
**「DB と同じホストに置くな」**であり、これは自宅内で解ける。

理由:

- 運用の想定が「解析者は現地に居ないかもしれない」に変わった以上、
  operator PC をハブにする設計は前提を失っている
- サーバは録画と CV のために**どのみち映像を必要としている**。
  いま operator ブラウザが JPEG に落として渡しているのは、
  ハブが operator だったことの副産物にすぎない
- 会場に PC がある場合の A は帯域と遅延で明確に優れるので、捨てずに残す
- ハブを自宅に置くと、TURN であれ SFU であれ待受を開けることになる。
  `denied-peer-ip` で中継悪用は防げると実証したが (5.5 節)、
  **プロセス自体を取られた場合は防げない**。DB と同居させない (5.7 節)

B (リモート PC ハブ) は**意図的に選ぶ対象ではない**。現行コードを遠隔で
使うと自動的に B になる、という事実を認識しておく必要がある。

### 段階

1. **プロトコルをハブ非依存にする** — **完了 (2026-08-15)**
   `stream_id` を導入し、宛先の解決をサーバ側へ移した。
   `media_hub` のセッション属性化は段階 3 と同時に行う
2. **operator を複数カメラ対応にする** — **完了 (2026-08-15)**
   `useCameraHub` が stream_id ごとに PeerConnection を持つ。
   A1〜A5 (単一 pcRef / 通知なし差し替え / viewer 取りこぼし / vpc リーク) を解消
3. **自宅内の隔離ノード (SFU + TURN) を立てる** — 5.7 節。
   NAT 越えとハブを同時に解く。`media_hub=isolated_hub` を選べるようにする。
   第1段は本番サーバ上の Hyper-V VM、第2段で専用機へ
4. **CV と録画の入力を購読へ移す** — operator ブラウザの JPEG 中継と
   端末の chunked upload をこの経路へ寄せる
5. **フォールバックと表示**

段階 1 と 2 はハブの選択に関係なく必要で、いま着手できる。
段階 3 は自宅に UDP を開ける判断を伴う。防御は実測済み (5.5) だが、
**開けたら必ず `verify_turn_hardening.py` で実挙動を確認する**。

## 5.5. SFU の実体 — 実測による判定 (2026-08-15)

### aiortc は SFU ではない (実装を読んで確認)

- `RTCRtpReceiver` は `decoder_worker` スレッドで**常に復号**し、
  `RemoteStreamTrack.recv()` は復号済み `Frame` を返す
- `MediaRelay` が配るのはその**復号済みフレーム**
- `RTCRtpSender` は `self.__encoder` を **sender ごとに 1 つ**持つ

したがってピアから受けた映像を転送する経路が無く、N カメラ × V 視聴者で
**N 回の復号 + N×V 回の再エンコード**になる。これは SFU ではなく
トランスコーダであり、遅延も画質劣化も増える。

`_next_encoded_frame` にはエンコード済みデータを `pack()` するだけの
分岐もあるが、これはローカル生成 (ファイル / GStreamer) の
`av.Packet` を流す場合の経路で、ピア受信には使えない。

### エンコード 1 本あたりの実測

aiortc の実エンコーダで 720p30 を計測 (12 コア Intel、149 フレーム、
静止画にならないよう平行移動 + ノイズを加えた素材):

| codec | ms/frame | 30fps 1 本あたり | ビットレート |
|---|---|---|---|
| VP8 | 13.67 | **41.0 % / 1 コア** | ~3500 kbps |
| H.264 | 7.41 | **22.2 % / 1 コア** | ~970 kbps |

カメラ 4 台 × 視聴者 4 人 = 16 本の送出で、H.264 でも **約 3.5 コア**を
エンコードだけで占有する (VP8 なら 6.5 コア超)。加えて受信 4 本の復号。
本番機は GPU で CV を回し PostgreSQL も抱えているので、
**aiortc をハブにする案は採らない。**

### さらに重要 — 中継以前に NAT 越えの問題がある

**WebRTC の映像は Cloudflare tunnel を通れない** (tunnel は HTTP/WS のみ)。
したがってサーバハブでもローカル PC ハブでも、会場と自宅の間で映像を流すには

- 自宅ルータで UDP ポートを開放する (今は tunnel 以外を露出していない)、または
- 公開アドレスを持つ **TURN 中継**を用意する

のどちらかが要る。**これは SFU を入れるかどうかとは独立に必要**で、
現状の「STUN のみ」構成では会場のゲスト Wi-Fi (UDP 遮断 / client isolation)
で映像が出ない。遠隔運用を選んだ時点で TURN は必須要件になっている。

### 候補の比較

| 案 | SFU | NAT 越え | 本番機の CPU | 備考 |
|---|---|---|---|---|
| aiortc | ✗ (トランスコード) | 別途 TURN 要 | 3.5 コア以上 | **却下** |
| LiveKit 自前 | ○ 真の SFU | **UDP ポート開放が必要** | 小 (Go・転送のみ) | Windows は Docker/WSL2 経由。自宅網の露出が増える |
| Cloudflare **TURN のみ** | — (ハブは別途) | ○ (開放不要) | ゼロ | 1000GB 無料枠。**Cloudflare は映像を復号できない** (5.6 節) |
| Cloudflare **SFU** | ○ | ○ (開放不要) | ゼロ | 同上の課金。ただし **SFU は構造上、映像を見られる** |
| SFU なし (ローカル PC ハブのみ) | — | 会場内で完結 | ゼロ | 会場に PC がある運用に限る |

概算では 4 カメラ × 3 視聴者・90 分の試合で egress 約 12 GB なので、
無料枠 1000GB/月の範囲に十分収まる。

**TURN と SFU を混ぜて考えないこと。** TURN は暗号文を転送するだけで
中身を見られないが、SFU は復号する。詳細は 5.6 節。

## 5.6. 暗号化 — どこまで端から端まで守れるか (2026-08-15)

### WebRTC に「非暗号化」は存在しない

WebRTC は仕様上 **DTLS-SRTP が必須**で、平文で流す設定が無い。鍵は
両端の DTLS ハンドシェイクで決まる。したがって「P2P でも暗号化されている
必要がある」という要件は、**追加実装なしで既に満たされている**。

問題は中継が入ったときに端から端までを保てるかで、ここが経路によって違う。

| 経路 | 中継者が映像を見られるか | 理由 |
|---|---|---|
| P2P 直 | — | 両端だけが鍵を持つ |
| **TURN 経由** | **見られない** | TURN は UDP を転送するだけ。DTLS は両端で終端し、TURN には暗号文しか届かない。見えるのは IP とポートのみ |
| **SFU 経由** | **見られる** | SFU は DTLS を終端し、購読者ごとに再暗号化する。**構造上そうせざるを得ない** |

Cloudflare の TURN も同じで、公式 FAQ が「DTLS により暗号化された状態で
中継され、Cloudflare が扱うのは接続管理に必要な IP / ポート等の
メタデータのみ」と明言している。
出典: https://developers.cloudflare.com/realtime/turn/faq/

**したがって前版の「Cloudflare Realtime は映像が第三者を通る」は
TURN については誤りだった。SFU を使う場合にのみ当てはまる。**

SFU でも端から端まで守りたい場合は E2EE (Insertable Streams / SFrame) が
要るが、その場合 SFU は中身を見られないので**サーバ側 CV も録画もできなくなる**。
本製品はサーバで解析することが目的なので、E2EE と目的が両立しない。

### 帰結

要件「NAT を越えたい」「自宅網を露出したくない」「映像を第三者に見せたくない」の
三つは、**TURN だけを使えば同時に満たせる**。SFU は満たせない。

したがって:

- **TURN は Cloudflare でよい** (無料枠 1000GB/月、STUN は無制限無料)。
  自宅ルータを一切開けず、かつ Cloudflare は映像を復号できない
- **SFU を第三者に置くのは、映像を見せることと同義**。自前に置くなら
  そこは信頼境界の内側になる

### 自前 UDP 公開を選ぶ場合の防御 (採るなら必須の項目)

「まともな防御はあるか」への答えは **ある**。ただし一点、外しやすい急所がある。

1. **公開するのは UDP のメディアポート範囲だけ**。signalling は今まで通り
   Cloudflare tunnel。HTTP/管理ポートは絶対に公開しない
2. **ICE 資格情報が門番になる**。WebRTC は STUN binding request に
   セッションごとの ufrag/pwd を要求し、合わないパケットは処理せず捨てる。
   一般的なポート開放より攻撃面はずっと狭い
3. **急所: TURN を内部ネットワークへの踏み台にされること。**
   **実測で確認済み** (`docs/validation/turn_relay_abuse_verification.md`)。
   既定の coturn は RFC1918 を拒否しないため、資格情報を持つ者は LAN 上の
   内部サービスへ実際に到達できた。塞ぐ経路は **CreatePermission と
   ChannelBind の 2 つ**あり、片方だけでは迂回される。
   `denied-peer-ip` で両方とも 403 になることも実測した。
   併せて `no-tcp-relay` を明示すること (TCP が通ると内部へ本物の
   TCP 接続を張られる)。設定ひな型は `infra/turn/coturn.conf.example`、
   本番確認は `infra/turn/verify_turn_hardening.py`
4. **資格情報は短命の HMAC 方式**にする。現行 `tunnel.py` は Settings の
   固定 TURN credential をそのまま返しており、これは踏み台化と
   帯域の踏み倒しを招く (codex 指摘済み・未修正)
5. **本番機に同居させない**。選手データと CV モデルを持つホストの隣に
   公開待受を置かない。別ホスト / VM / VLAN へ
6. `user-quota` / `total-quota` / `max-bps` で使用量を縛る
7. `no-cli` で管理インターフェースを無効化。割当数と転送量を監視する

これらは標準的な運用で、成立はする。それでも **まず Cloudflare TURN を試すべき**
なのは、同じ接続性をゼロ露出・ゼロ運用で得られるから。自前が要るのは
「Cloudflare にメタデータ (誰がいつどこから繋いだか) すら渡したくない」場合。

### miasma-protocol の資産は転用できるか

結論: **直接は転用できない。** あちらは libp2p / DHT / onion routing による
蓄積型コンテンツ配送で、遅延許容が桁違いに大きい。リアルタイム映像は
RTP + ジッタバッファの世界で要求が別物。

ただし概念は同じで、miasma の「relay circuit」「rendezvous」は
本質的に TURN と同じ役割 (到達不能なピアを中継で繋ぐ) を果たしている。
制限の強いネットワークを越える運用知見は参考になる。

## 5.7. 自宅内隔離ハブ構成 (推奨案・2026-08-15)

**外部の事業者と契約しない。** 本プロジェクトは個人の自宅サーバで完結させる
方針であり、VPS も Cloudflare Realtime も選択肢から外す。
(初版はここに VPS を据えていたが、前提の確認漏れだったので差し替えた)

したがって **TURN は自宅に置き、UDP を開ける**。5.5 で検証したとおり中継悪用は
`denied-peer-ip` で防げる。残る問題は 5.6 の「coturn プロセス自体を取られたら
ACL は無関係になり、DB と同居していれば loopback で `127.0.0.1:5432` に届く」で、
これは**外部に出さなくても「DB と同じホストに置かない」ことで解ける**。

```
  会場のカメラ ──(UDP)──> メディア/解析ノード ──(本番サーバが取りに行く)──> 本番サーバ
  遠隔の視聴者 <───────────  SFU + TURN + CV                              DB / アプリ / トンネル
```

### 置き場所を「専用機」と考えない

SFU は**どのみち映像を復号する**。つまりそのノードには生の映像が既にある。
一方で現状の CV は operator のブラウザが 640×360 / JPEG q0.55 / 10fps に
落としたものを食べている (2 節)。

**映像を受け取るノードで CV を回すのが本来の形**であり、SFU を置いた時点で
そこに映像がある以上、CV を隣に置いても露出は増えない。得られるもの:

- CV がフル解像度の実ストリームを得る (解析品質が operator のブラウザに
  依存しなくなる)
- 本番サーバから GPU 負荷が降りる
- operator が JPEG 中継から解放される

「TURN のために 1 台遊ばせる」のではなく、**本番サーバの仕事を 1 つ引き取る**。

### データの向き

**メディアノードから本番サーバへは接続させない。本番サーバ側から取りに行く。**
固定スキーマ・サイズ上限・コマンド実行なしの読み取り専用経路にする。
これによりメディアノードが完全に侵害されても DB へ向かう道が無い。

メディアノードに置かないもの:

- 本番 DB の資格情報、`.env`、バックアップへの経路
- Cloudflare tunnel の token
- 本番サーバへ入れる SSH 鍵
- アプリのソース、選手データ

参加認可は**非対称鍵**で行う。本番サーバが秘密鍵で署名した短命トークンを
参加者に配り、メディアノードは公開鍵で検証するだけにする。
共有 secret だとノードの侵害がそのまま発行権限の奪取になる。

### 段階

**第 1 段: 本番サーバ上の Hyper-V VM (当面これで進める)**

追加ハードウェア不要。ただし**分離は一段弱い**ことを明記しておく。

- 守れる: 開いた UDP から入った攻撃者が LAN や DB へ横移動すること
- 守れない: VM 脱出、仮想スイッチの設定ミス
- 「選手の映像とデータを持つホストの上に公開待受を置く」ことに変わりはない

構成上の注意 (ここを誤ると分離が成立しない):

- 仮想スイッチは **External を使わない**。External は VM を LAN に直結させる
  ため隔離にならない。**Internal スイッチ + ホスト側 NAT** (`New-NetNat`) を使う
- Internal + NAT では、既定で **VM からホスト経由で LAN へ到達できる**。
  ホストのファイアウォールで **VM サブネット → LAN サブネットを明示的に拒否**
  すること。これが最も見落としやすい
- ポート転送はルータ → ホスト → VM の 2 段になる。UDP なので
  `netsh portproxy` は使えない (TCP 専用)。`New-NetNatStaticMapping` を使う
- coturn には `external-ip` でグローバル側アドレスを教える

**第 2 段: 専用機 (i9-13900HK / RAM 64GB / 5060Ti eGPU) へ移す**

物理的に分離され、VM 脱出の懸念が消える。GPU があるので CV もこのノードへ
移し、上記の「メディア/解析ノード」構成が完成する。

### 設定後に必ず行うこと

**UDP を開けたら `infra/turn/verify_turn_hardening.py` を実際のノードへ向けて
走らせ、終了コード 0 を確認する。** 設定の字面で判断しない。
ルータ → ホスト → VM の 2 段転送は誤りが入りやすく、
`denied-peer-ip` には無効化される罠が 3 件ある (5.5 / 検証記録)。


## 6. 未決事項

- SFU の実体: **aiortc は実測により却下** (5.5 節)。隔離ノード上で動かす
  実体を選ぶ (LiveKit / mediasoup / Janus)。**未選定**
- Hyper-V の Internal スイッチ + NAT で、VM → LAN を実際に遮断できるかの実測。
  「設定したつもり」で通っている状態が最も危ない (5.7 節)
