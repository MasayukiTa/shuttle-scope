# Round 258 R20 — R19 直後監査の P1/P2 を回収

## 概要

R19 (68b8d6b) を 1 体の独立 agent で再監査。R19 で導入した変更そのものに 2 件の P1 fail-open / 検証漏れが見つかり、加えて R7-R19 全期間で見落としていた P2 が 3 件報告された。本 R20 では:

- **P1: 2 件**（両方とも R19 自身の regression）
- **P2: 2 件**（password rotation 後の access token 残存 / loopback upload 上限欠如）

を 1 commit にまとめて closed。残 P2 (asyncio.to_thread shutdown leak) と P3 3 件は R21 backlog。

## 修正一覧

### R20 P1-1 — `mirror-broadcast` IPC sender gate fail-open

| | |
| --- | --- |
| 影響 | R19 で導入した sender gate に2 つの欠陥 — (a) `senderFrame?.parent != null` は `senderFrame === null` のとき `undefined != null === false` で素通し、(b) `mainWindow?.isDestroyed() === false &&` は mainWindow が null/destroyed のとき短絡で 2nd guard 自体を skip。両方が同時に成立する状態 (起動直後 / splash 切替 / window 破棄中) で stale な webContents から任意 mirror-message を全 window に注入可能 |
| ファイル | `shuttlescope/electron/main.ts` (mirror-broadcast IPC handler) |

**修正方針**:
- `if (!senderFrame || senderFrame.parent != null) return` で fail-closed。
- `if (!mainWindow || mainWindow.isDestroyed()) return` を独立行に出す。
- その後 `event.sender.id !== mainWindow.webContents.id` を必ず実行。

### R20 P1-2 — WS operator reverify が `receive_text()` 待ちで idle 中は走らない

| | |
| --- | --- |
| 影響 | R19 で 60s 周期 reverify を実装したが、`await websocket.receive_text()` の **return 後** にしか reverify を駆動していなかった。idle な (送信無し) operator は永久に reverify が走らず、admin が token を mass_revoke / 個別 revoke しても camera signaling slot を持ち続け、device からの inbound traffic を relay し続ける |
| ファイル | `shuttlescope/backend/ws/camera.py` |

**修正方針**:
- `asyncio.wait_for(websocket.receive_text(), timeout=60)` で受信側に timeout を仕込む。
- TimeoutError 経由でも `_do_reverify_and_close_if_invalid()` を呼んで idle 状態でも reverify が確実に駆動される。
- 受信成功時は `_last_reverify` で interval 単位 throttle (busy traffic でも DB 負荷を抑制)。

### R20 P2-2 — password change が access token (15min) を失効しない

| | |
| --- | --- |
| 影響 | 旧 `change_password` / `admin_reset_password` は `revoke_all_refresh_tokens_for_user` のみ呼んでおり、access token (15min) は残存。password 変更が incident response の手段として呼ばれたとき、盗まれた access token が 15 分間使い続けられる |
| ファイル | `shuttlescope/backend/utils/jwt_utils.py` (`_get_user_revoke_timestamp`, `revoke_all_for_user` 新規追加) / `shuttlescope/backend/routers/auth.py` (change_password / admin_reset_password) |

**修正方針**:
- `revoked_tokens` テーブルの jti プレフィックスに `__user_revoke_<user_id>_<isoformat>` を追加 (mass_revoke の per-user 版)。
- `_get_user_revoke_timestamp(user_id)` を 5s TTL + LRU 4096 キャッシュで実装。
- `verify_token` の iat 検査直後に per-user revoke check を追加 → 該当 user の old iat を持つ token は reject。
- `change_password` / `admin_reset_password` から `revoke_all_for_user(user.id)` を呼び、sentinel を書き in-process cache を即時無効化。

トレードオフ: 5s cache は cross-process gap として残る (mass_revoke と同じ trade-off)。in-process cache は password 変更時に即時無効化されるので呼び出し元プロセスから即時に効果。

### R20 P2-3 — loopback (`ctx.user_id is None`) 経路で upload 並列上限 bypass

| | |
| --- | --- |
| 影響 | `ALLOW_LOOPBACK_NO_AUTH=1` では loopback の caller は `user_id=None` で動作するが、旧 init_upload は `if ctx.user_id is not None` で per-user cap を skip していた。total_size=5GB の sparse `.part` を多数 truncate されて volume DoS |
| ファイル | `shuttlescope/backend/routers/uploads.py` |

**修正方針**: `ctx.user_id is None` 専用の弱い cap (`_MAX_CONCURRENT_LOOPBACK = 4`) を追加し、`UploadSession.user_id IS NULL AND status == "uploading"` の数で gate。

### Manual (本番デプロイ後)
- `attacktest/round258_r20_idle_ws_revoke.py`: operator として WS 接続後、メッセージを送らず admin で token revoke → 60s 以内に 4401 で close されること。
